# Rule 1 - 每次執行必須重置執行紀錄

- 進入任務批次前，必須在目標 feature 目錄建立或覆寫 `implement-run.md`。
- 重置後的 `批次起點`、`失敗原因`、`阻塞`、`恢復條件` 必須為空白。
- 不得保留上一次執行的阻塞或失敗原因。

## Good Example

- 新的一次執行覆寫舊紀錄，四個欄位都是空白。

```markdown
批次起點：
失敗原因：
阻塞：
恢復條件：
```

## Bad Example

- 新的一次執行沿用上一次留下的阻塞。

```markdown
批次起點：T019
失敗原因：frontend/catalog.test.ts 既有失敗
阻塞：範圍外失敗
恢復條件：修好 frontend/catalog.test.ts 後，重新執行 implement
```

# Rule 2 - 失敗原因與阻塞必須分開記錄

- 仍要修正並重新驗證的失敗，必須只更新 `失敗原因`。
- 仍要修正並重新驗證時，`阻塞` 與 `恢復條件` 必須保持空白。
- 無法再修正的失敗，必須寫入 `阻塞` 與 `恢復條件`。
- `恢復條件` 必須寫明解除該阻塞後重新執行 implement。
- 範圍外失敗的 `恢復條件` 必須指出要先修好的失敗項目。
- 完成本次失敗原因與紀錄中既有 `失敗原因` 的比較前，不得覆寫 `失敗原因`。
- 不得把尚未確定停止的失敗原因寫入 `阻塞`。
- `阻塞` 已不是空白時，不得覆寫既有 `阻塞` 與 `恢復條件`。
- 不得只把停止依據寫進回覆而不寫入 `implement-run.md`。

## Good Example

- 第一次 Checkpoint 失敗仍要修正，所以只更新失敗原因。

```markdown
批次起點：驗證 Phase 2 Checkpoint
失敗原因：session 建立失敗
阻塞：
恢復條件：
```

## Bad Example

- 第一次 Checkpoint 失敗仍要修正，卻已寫成阻塞。

```markdown
批次起點：驗證 Phase 2 Checkpoint
失敗原因：session 建立失敗
阻塞：Checkpoint 驗證失敗
恢復條件：重新執行 implement
```

# Rule 3 - 後續判斷必須讀取執行紀錄

- 決定是否繼續下一批前，必須讀取 `implement-run.md` 的 `阻塞`。
- 回報本次執行前，必須讀取 `implement-run.md` 的 `阻塞` 與 `恢復條件`。
- 選定批次後，必須把該批次起點寫入 `批次起點`。
- 進入下一個批次前，必須清除上一個批次的 `失敗原因`。
- 同一任務或同一個 Checkpoint 重新驗證前，不得清除尚待比較的 `失敗原因`。
- 不得從 `tasks.md` 讀取阻塞事項。

## Good Example

- 繼續判斷讀取執行紀錄裡的空白阻塞，並清除上一個批次的失敗原因。

```markdown
批次起點：T018
失敗原因：
阻塞：
恢復條件：
```

## Bad Example

- 繼續判斷改從 `tasks.md` 尋找阻塞，執行紀錄仍留著上一個批次的失敗原因。

```markdown
批次起點：T017
失敗原因：one-a-two-b.test.ts B-count duplicate handling
阻塞：
恢復條件：
讀取來源：tasks.md
```
