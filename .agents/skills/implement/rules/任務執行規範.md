# Rule 1 - 變更範圍必須只滿足目標任務

- 原始碼、測試或文件變更必須直接服務於目標任務的描述與 `References`。
- 可以建立目標任務需要的最小輔助型別、函式或檔案。
- 不得實作未納入本批次的下一個未完成任務描述的行為。
- 不得把 unrelated refactor、格式化全專案或依賴升級混入目標任務。

## Good Example

- T019 只實作計分純函式，不處理未納入批次的 WebSocket 分派。

```markdown
目標任務：T019 在 backend/src/game/one-a-two-b.ts 實作 scoreGuess
本次變更：scoreGuess 與四碼不重複驗證
未做：submit_guess 狀態機、WebSocket 推送
```

## Bad Example

- T019 順手實作未納入批次的 T020 與 T022 行為。

```markdown
目標任務：T019 在 backend/src/game/one-a-two-b.ts 實作 scoreGuess
本次變更：scoreGuess、submit_guess、WebSocket connection 分派
```

# Rule 2 - 測試任務必須先看到失敗

- 目標任務是測試任務時，必須先寫入該測試任務要求的斷言。
- 新測試必須在對應實作完成前執行並取得預期失敗結果。
- 測試失敗原因必須對應尚未實作的目標行為，不得是語法錯誤、錯誤 import 或測試環境缺失。
- 若新測試無法執行到有效失敗，必須修正測試任務本身，不能將任務打勾。

## Good Example

- 測試失敗原因是 `scoreGuess` 尚未實作。

```text
FAIL one-a-two-b.test.ts
Expected { aCount: 4, bCount: 0 }
Received { aCount: 0, bCount: 0 }
```

## Bad Example

- 測試失敗原因是 import path 錯誤，不能視為有效紅燈。

```text
FAIL one-a-two-b.test.ts
Cannot find module "../src/game/one-a-two-b"
```

## Exceptions

- 任務標有 **TDD 步驟** 時，失敗測試的寫入與確認必須交給 `tdd`，不由本規則的寫入要求執行。

# Rule 3 - 實作任務必須優先滿足既有測試與契約

- 目標任務是實作任務時，必須先找出對應測試任務或最小契約驗證方式。
- 實作必須滿足已選任務列出的契約部位與錯誤路徑。
- 不得修改測試來配合錯誤實作，除非測試本身與契約矛盾。
- 若測試與契約矛盾，必須回報矛盾並停止或只修正明確錯誤的測試。

## Good Example

- 實作依 `GuessRecord` 契約回傳 `aCount` 與 `bCount`。

```typescript
return { aCount, bCount };
```

## Bad Example

- 實作回傳未在契約中的欄位，並改測試接受它。

```typescript
return { exactMatches, partialMatches };
```

## Exceptions

- 任務標有 **TDD 步驟** 時，最小實作的寫入必須交給 `tdd`，不由本規則的寫入要求執行。
