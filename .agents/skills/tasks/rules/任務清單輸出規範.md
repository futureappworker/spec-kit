# Rule 1 - 任務清單的輸出位置

- 任務清單必須寫入該功能 `plan.md` 所在目錄的 `tasks.md`。
- 不得把任務清單寫進 Skill 的 `templates/`。
- 不得另建與 `tasks.md` 並列的第二份任務清單。

## Good Example

- 任務清單與該功能的 plan.md 放在同一目錄。

```text
specs/001-store-checkout/tasks.md
```

## Bad Example

- 任務清單寫進 Skill 樣板目錄，沒有落在功能目錄。

```text
.agents/skills/tasks/templates/tasks.md
```

# Rule 2 - 階段與端點層級

- 任務清單必須依序包含 Phase 1 Setup、Phase 2 Foundational、每個使用者故事一個 Phase、以及最後的 Polish Phase。
- 使用者故事 Phase 的數量必須等於 spec.md 的使用者故事數量。
- 使用者故事 Phase 與 Polish Phase 必須用 `###` 依 plan.md「系統介面盤點」切開端點。
- 端點小節必須包含 **Codebase**。端點小節不得列出契約檔或 **References**。
- 某個端點在該故事沒有任務落點時，不得為它開空的端點小節。
- 有測試的端點必須排在同故事的其他端點之前。
- 骨架與範例中的三則故事、T001 到 T054，以及後端、資料庫、前端三個名稱，是已確認範例的填法。產出時必須改成這次 spec.md 與 plan.md 的故事與端點，不得照抄範例任務。

## Good Example

- 故事數量跟 spec.md 一致，端點名稱跟 plan.md 盤點一致，而且沒有空端點。

```markdown
## Phase 3: User Story 1 - 由待結帳購物車建立訂單（Priority: P1）

### 後端端點：商品、購物車與訂單 HTTP API

**Codebase**: `backend/src/orders/`、`backend/tests/`
```

## Bad Example

- 不管 spec.md 有幾則故事都照抄三則，並為沒有資料庫任務的故事加一個空的資料庫端點。

```markdown
## Phase 5: User Story 3 - 設定收件地址與配送方式（Priority: P3）

### 資料庫端點：PostgreSQL 持久化介面

**Codebase**: `backend/src/db/`
```

# Rule 3 - 每個任務只綁本端點的部位

- 每個任務正下方必須有 **References**。
- 一行 **References** 只能有一個位址。
- 位址必須定位到單一部位：OpenAPI 的一個 schema 或一個 path operation、DBML 的一個 Table、畫面的一個 frame id、`techstack.md` 採用技術表的一個 Area，或 plan.md 的一個標題。
- 任務只實作一個部位時，只能有一行 **References**。
- 任務直接實作或斷言同一份文件裡的多個部位時，每個部位各一行，而且必須屬於同一個端點的契約。
- 後端任務不得引用 DBML 或畫面。資料庫任務不得引用 OpenAPI 或畫面。前端畫面任務不得引用 OpenAPI 或 DBML。
- 沒有獨立 payload schema 的操作，必須改指該操作結果所屬的那一個 schema，不得改指整份 OpenAPI。
- 端點小節與任務清單開頭不得要求先讀完整份 research.md、techstack.md 或 contracts/。

## Good Example

- 儲存收件地址的後端任務只指向 SaveAddressRequest。

```markdown
- [ ] T037 [US3] 在 `backend/src/cart/cart-service.ts` 實作 `save_address`
  - **References**: `contracts/openapi.yaml#/components/schemas/SaveAddressRequest`
```

## Bad Example

- 端點小節一次列出整份 OpenAPI，任務本身沒有位址。

```markdown
### 後端端點：商品、購物車與訂單 HTTP API

**References**: 進入本節才載入 `contracts/openapi.yaml`。

- [ ] T037 [US3] 在 `backend/src/cart/cart-service.ts` 實作 `save_address`
```

# Rule 4 - 測試先於同故事的實作

- 使用者可觀察行為的測試任務必須寫在擁有該行為的端點小節裡，並排在該端點的實作任務之前。
- 測試任務不得集中到清單最後的 Polish Phase，除非該測試驗證的是跨故事行為。
- 同一端點小節裡必須先列出 **Tests**，再列出 **Implementation**。

## Good Example

- 訂單金額的測試在後端端點裡，而且排在計價實作之前。

```markdown
**Tests**:

- [ ] T017 [P] [US1] 在 `backend/tests/unit/pricing.test.ts` 撰寫金額單元測試
  - **References**: `contracts/openapi.yaml#/components/schemas/OrderTotals`

**Implementation**:

- [ ] T019 [P] [US1] 在 `backend/src/orders/pricing.ts` 實作純函式計價
  - **References**: `contracts/openapi.yaml#/components/schemas/OrderTotals`
```

## Bad Example

- 測試被留到所有故事做完之後才出現。

```markdown
## Phase 6: Polish & Cross-Cutting Concerns

- [ ] T099 補寫全部使用者故事的測試
```
