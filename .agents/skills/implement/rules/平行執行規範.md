# Rule 1 - 平行批次必須有明確准入依據

- 同一批次中的多個任務必須被 `[P]` 標記、或被 `Parallel Opportunities` 明確列為可平行、或可由檔案與依賴判斷證明可平行。
- 平行任務必須位於同一個 Phase gate 與同一個 checkpoint 邊界內。
- 平行任務不得共享寫入目標檔案。
- 無法證明安全平行時，必須把批次縮小到單一任務。

## Good Example

- T017 與 T018 都是測試任務、不同檔案、同一 checkpoint 前，因此可以同批次平行執行。

```markdown
- [ ] T017 [P] [US1] 在 backend/tests/unit/one-a-two-b.test.ts 撰寫測試
- [ ] T018 [P] [US1] 在 backend/tests/integration/submit-guess.test.ts 撰寫測試

本次目標批次：T017、T018
```

## Bad Example

- 兩個任務都會修改同一檔案，不能放入同一平行批次。

```markdown
- [ ] T020 [US1] 在 backend/src/game/room-state-machine.ts 實作 submit_guess
- [ ] T029 [US2] 在 backend/src/game/room-state-machine.ts 實作 join_match

本次目標批次：T020、T029
```

# Rule 2 - 有順序關係的任務必須序列化

- 測試任務與其對應實作任務不得放入同一批次。
- 同一案例的紅燈、綠燈與重構不得放入同一批次。
- 服務層實作與依賴該服務的路由、WebSocket 分派或前端串接不得放入同一批次。
- Schema、型別或 migration 任務與依賴該結構的實作任務不得放入同一批次。
- 任務描述、Dependencies 或 Within Each User Story 指出順序時，必須依該順序序列化。

## Good Example

- 先選測試任務，實作任務留到下次批次。

```markdown
- [ ] T017 [P] [US1] 撰寫 scoreGuess 測試
- [ ] T019 [P] [US1] 實作 scoreGuess

本次目標批次：T017
下一批候選：T019
```

## Bad Example

- 把測試與對應實作放進同一批次，失去先紅後綠的驗證邊界。

```markdown
- [ ] T017 [P] [US1] 撰寫 scoreGuess 測試
- [ ] T019 [P] [US1] 實作 scoreGuess

本次目標批次：T017、T019
```

# Rule 3 - 平行只放大安全的讀取與獨立執行

- 可以平行執行不會修改檔案的上下文讀取與診斷讀取。
- 可以平行執行互不依賴且不會互相修改輸出的測試、lint 或 typecheck。
- 可以平行修改不同檔案，但每個任務仍必須保留各自的 References、變更摘要、驗證證據與 checkbox。
- 不得用一次總驗證取代每個任務的通過證據。

## Good Example

- 同批任務各自修改不同檔案，且各自保留驗證證據。

```markdown
本次目標批次：T017、T018
T017 驗證：one-a-two-b.test.ts 取得預期失敗
T018 驗證：submit-guess.test.ts 取得預期失敗
```

## Bad Example

- 批次中多個任務只使用一個含糊的總結結果，無法判斷各任務是否完成。

```markdown
本次目標批次：T017、T018
驗證：npm test 失敗，應該有測到兩個任務
```
