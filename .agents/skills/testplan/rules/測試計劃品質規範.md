# Rule 1 - 上游介面索引

- 案例引用到的每個上游介面必須在索引表各出現一次。
- 索引表必須包含介面、`plan.md` 盤點與契約三欄。
- 盤點欄必須指向 `plan.md` 系統介面盤點中已有的端點。
- 契約欄必須指向該介面的契約檔。
- 測試計劃不得重寫呼叫契約、公開介面清單、本介面涵蓋或留給其他介面。
- 案例的受測操作必須已經存在於該案例契約位址指向的契約檔。
- 測試計劃不得包含測試程式碼、SQL 或斷言函式呼叫。

## Good Example

- 索引只指向既有盤點與契約檔，案例另寫預期輸出。

```markdown
| 介面 | plan.md 盤點 | 契約 |
| --- | --- | --- |
| 後端房間 API | 系統介面盤點的後端端點「後端房間 API」 | `contracts/openapi.yaml` |
```

## Bad Example

- 同一介面改寫呼叫契約與公開操作清單，計劃變成第二份系統分析。

```markdown
**呼叫契約 ( Call Contract )**：進入成功回傳 `playerId`。
**公開介面 ( Public Interface )**：
- `POST /api/rooms/enter`
```

# Rule 2 - User Story 與跨故事章

- `spec.md` 的每一則使用者故事必須各成一章，並沿用該故事的標題與優先級。
- 不屬於單一使用者故事的全域需求與成功標準必須放在一個跨故事章。
- 沒有可測試案例的跨故事章不得建立。
- 每個使用者故事章與跨故事章必須各自有一份 TDD 順序。
- 該章 TDD 順序必須列出該章每個原子案例恰好一次。
- TDD 順序是該章的執行順序。
- 受測部位不含「瀏覽器」的案例必須全部排在 `#### 單元與服務測試`。
- 受測部位包含「瀏覽器」的案例必須全部排在 `#### 瀏覽器端到端測試`，且必須排在該章單元與服務測試之後。
- 某一段沒有案例時，必須省略該小標，不得留下空清單。

## Good Example

- 進房故事先列該章的服務案例，再列該章的瀏覽器案例。

```markdown
## 使用者故事 1 - 以暱稱與房號進入房間（Priority: P1）

### TDD 順序 ( Atomic Order )

#### 單元與服務測試

1. BE-1.1
2. BE-3.1

#### 瀏覽器端到端測試

1. FE-1.1
```

## Bad Example

- 同一進房故事把瀏覽器案例排在服務案例之前，且沒有分成兩段。

```markdown
## 使用者故事 1 - 以暱稱與房號進入房間（Priority: P1）

### TDD 順序 ( Atomic Order )

1. FE-1.1
2. BE-1.1
3. BE-3.1
```

# Rule 3 - 共用 Arrange Fixtures

- 兩個以上案例共用的前置狀態必須定義成共用 Arrange Fixture。
- Fixture 必須寫出可執行的前置操作，並保留後續呼叫需要的識別值。
- 案例的前置條件必須引用 Fixture 名稱。
- 只被一個案例使用的前置必須寫在該案例內，不得為它建立共用 Fixture。

## Good Example

- 兩個進房案例都引用已定義的空資料庫 Fixture。

```markdown
- **前置條件 ( Arrange )** Fixture 空資料庫。
```

## Bad Example

- 只有一個案例需要等待中的房主，卻把這段前置抽成共用 Fixture。

```markdown
1. **Fixture 等待房主**：玩家A 呼叫 `POST /api/rooms/enter`。
```

## Exceptions

- 案例要分辨的輸入與共用 Fixture 的字面值衝突時，該段前置寫在案例內。

# Rule 4 - 原子案例

- 一個案例必須只有一個唯一測試意圖。
- 一個案例要同時驗證兩個以上可分開觀察的結果時，必須拆成多個原子案例。
- 每個案例必須包含對應需求、契約位址、唯一測試意圖、受測部位、受測操作、前置條件、操作、觀測通道、預期輸出、必須維持不變、本案例不驗證、預期 RED 原因。
- 每個案例的契約位址必須只有一個，且必須是該案例受測操作的位址。
- 操作必須寫出這次送出的具體輸入，包含會影響規則判斷的字面值。
- 對應需求只索引規格。斷言要用的字面值必須寫在 Fixture、操作或預期輸出。

## Good Example

- 進房案例只指向進入房間這個操作，並寫出暱稱與房號。

```markdown
- **契約位址 ( Contract )** `contracts/openapi.yaml#/paths/~1api~1rooms~1enter/post`
- **受測操作 ( Operation )** `POST /api/rooms/enter`
- **操作 ( Act )** `nickname` 為「玩家A」，`roomCode` 為「1234」。
```

## Bad Example

- 同一個案例同時要求建立房間、揭曉祕密答案與留下猜測紀錄。

```markdown
### BE-1.1 建立房間、揭曉祕密答案並留下猜測紀錄
```

## Exceptions

- 當案例對應的是 NFR 時，契約位址必須指向該品質需求所約束的既有操作。預期輸出必須寫規格原文已有的品質結果。不得要求契約另有一個 NFR 專用操作。

# Rule 5 - Oracle

- 預期輸出的每一項事實必須能對到該案例的觀測通道。
- 必須維持不變必須只列這次要斷言、且與操作前相同的欄位；沒有時必須寫「無」。
- 本案例不驗證列出的項目不得寫進預期輸出或必須維持不變。
- 每個案例必須寫預期 RED 原因，指出這個案例尚不存在時會失敗的觀察。

## Good Example

- 進房案例只斷言這次進入回應，並把祕密答案放在本案例不驗證。

```markdown
- **預期輸出 ( Expected Output )** HTTP 201。`role` 為房主。
- **必須維持不變 ( Must Stay )** 無。
- **本案例不驗證 ( Not Verified )** 祕密答案、猜測紀錄。
```

## Bad Example

- 本案例不驗證已排除祕密答案，預期輸出仍要求 `ownSecret`。

```markdown
- **預期輸出 ( Expected Output )** HTTP 201。`ownSecret` 為 5678。
- **本案例不驗證 ( Not Verified )** 祕密答案。
```

# Rule 6 - NFR 與不列為案例

- 規格原文已有可觀察結果的 NFR，必須寫成與 FR 相同欄位的原子案例。可觀察結果包含時間、數量、畫面上的狀態，或失敗後仍須保留的資料。
- 該 NFR 案例的契約位址必須指向被約束的既有操作。預期輸出必須寫該品質結果。
- 測試計劃不得替規格補上它沒寫的門檻、秒數、次數或文案。
- 該 NFR 案例必須放在所屬使用者故事章；不屬於單一故事時放在跨故事章，並進入該章 TDD 順序。
- 規格原文沒有上述可觀察結果的 NFR，必須在所屬章列為不列為案例，並寫出原因。
- 不列為案例不得進入該章 TDD 順序。

## Good Example

- 規格寫了開始後 1 秒內看得到對局中，所以契約位址指向既有的開始操作，預期輸出寫 1 秒。

```markdown
- **對應需求 ( Traces )** NFR-US2-001
- **契約位址 ( Contract )** `contracts/interface.pen#in-match`
- **受測操作 ( Operation )** 房主按「開始對局」
- **預期輸出 ( Expected Output )** 房主按下開始後 1 秒內，雙方畫面都顯示「對局中」。
```

## Bad Example

- 同一條 1 秒 NFR 因契約沒有專用操作而被排除，沒有進入 TDD 順序。

```markdown
### 不列為案例

- **NFR-US2-001**：開始後 1 秒內顯示對局中。原因：契約沒有 NFR 專用操作。
```

# Rule 7 - 重複單元

- 介面、Fixture、使用者故事、案例與不列為案例的數量必須依上游輸入增減。
- 增減任一單元時，必須保留骨架中該單元的欄位與層級。
- 不得省略案例欄位，也不得新增骨架沒有的案例欄位。

## Good Example

- 需求只有一個故事與一個案例時，仍保留該案例的全部欄位。

```markdown
### BE-1.1 建立房間
- **對應需求 ( Traces )** FR-US1-001
- **契約位址 ( Contract )** `contracts/openapi.yaml#/paths/~1api~1rooms~1enter/post`
- **唯一測試意圖 ( Intent )** 不存在的房號會開出房間。
- **受測部位 ( Subject )** 後端房間 API
- **受測操作 ( Operation )** `POST /api/rooms/enter`
- **前置條件 ( Arrange )** Fixture 空資料庫。
- **操作 ( Act )** `nickname` 為「玩家A」，`roomCode` 為「1234」。
- **觀測通道 ( Observation Channel )** 這次進入的回應。
- **預期輸出 ( Expected Output )** HTTP 201。`role` 為房主。
- **必須維持不變 ( Must Stay )** 無。
- **本案例不驗證 ( Not Verified )** 第二位玩家。
- **預期 RED 原因 ( Expected Red )** 進入回應不是 HTTP 201 的房主。
```

## Bad Example

- 案例只留下意圖與預期，省略契約位址、操作與預期 RED 原因。

```markdown
### BE-1.1 建立房間
- **唯一測試意圖 ( Intent )** 不存在的房號會開出房間。
- **預期輸出 ( Expected Output )** HTTP 201。
```

# Rule 8 - 畫面流程的受測部位是瀏覽器

- 使用者在畫面上完成的流程，受測部位必須包含「瀏覽器」。
- 該案例不得把受測部位寫成前端元件、前端畫面或其他不含「瀏覽器」的名稱。
- 該案例不得寫成可以 mock、替身或改接受測應用自己的 HTTP 或 WebSocket。
- 不開瀏覽器的案例，受測部位不得包含「瀏覽器」。

## Good Example

- 進房後要在畫面上看到等待對手，受測部位寫明瀏覽器，操作是按畫面上的按鈕。

```markdown
- **受測部位 ( Subject )** 瀏覽器對局畫面
- **受測操作 ( Operation )** 按「進入房間」
- **操作 ( Act )** 在「暱稱」填玩家A、在「房號」填 1234，按「進入房間」。
- **觀測通道 ( Observation Channel )** 畫面上的「房間狀態」。
```

## Bad Example

- 同一進房畫面改測前端元件，並允許 mock WebSocket。

```markdown
- **受測部位 ( Subject )** 前端對局畫面
- **受測操作 ( Operation )** 渲染進入房間後的元件
- **操作 ( Act )** 以 mock WebSocket 注入已進入房間的狀態。
- **觀測通道 ( Observation Channel )** 元件上的房間狀態文字。
```
