# implement

依 feature 目錄中的 `tasks.md` 連續執行安全任務批次，直到任務全部完成。每個任務只讀該任務列出的 References，驗證通過後才打勾。Checkpoint 驗證失敗時，先修正所屬任務再重新驗證。

執行入口是 [SKILL.md](SKILL.md)。本文件說明這個 Skill 怎麼選任務、怎麼驗證，以及什麼時候停下來。

## 輸入

- 目標 feature 目錄，或目前功能目錄。任務清單是該目錄的 `tasks.md`。
- 同目錄 `plan.md`：原始碼落地位置、系統介面盤點、技術棧與驗證線索。
- 使用者可指定任務 ID。該 ID 標示關注的任務；執行仍從第一個前置條件已滿足的未完成任務開始，並一直做到清單完成。
- 使用者可允許略過未完成的 checklist。未允許時，feature 目錄的 `checklists/` 若有未勾選項目，本次寫出狀態與是否繼續的問題，然後停止。
- 專案根目錄的套件、測試、lint 與格式化設定，用來決定可用的驗證命令。

## 執行紀錄

每次執行開始時，在目標 feature 目錄建立或覆寫 `implement-run.md`，四個欄位都空白：

```markdown
批次起點：
失敗原因：
阻塞：
恢復條件：
```

- `批次起點`：選定批次後寫入。
- `失敗原因`：仍要修正並重新驗證時才更新。進入下一個批次前清除。同一任務或同一個 Checkpoint 重新驗證前，保留尚待比較的失敗原因。
- `阻塞` 與 `恢復條件`：無法再修正時才寫入。`阻塞` 已有內容時保持原內容。`恢復條件` 寫明解除阻塞後重新執行 implement；範圍外失敗要指出先修好的項目。

後續是否繼續，以及最後回報，都讀這份紀錄。

## 執行流程

1. 讀取 feature 目錄、任務 ID、是否略過 checklist，以及 `tasks.md` 與 `plan.md`。
2. 重置 `implement-run.md`。
3. 檢查 checklist。有未完成項且未允許略過時停止。
4. 選出一個安全任務批次，或只驗證下一個 Checkpoint，並把批次起點寫入執行紀錄。
5. 實作批次逐任務載入 References 與目標原始碼，決定變更範圍與完成判定。
6. 測試任務先寫斷言並取得預期失敗；實作任務再寫入最小變更。
7. 逐任務驗證。通過才把該任務的 `[ ]` 改成 `[X]`。
8. 需要時驗證 Checkpoint。通過則在 Checkpoint 下一行寫入 `**Checkpoint status**: PASS`，並清除 `失敗原因`。
9. Checkpoint 失敗時，在所屬任務範圍內修正，再回到 Checkpoint 驗證。
10. `阻塞` 為空白且仍有未完成工作時，清除上一個批次的失敗原因，立刻開始下一批。否則回報並結束。

批次之間繼續下一個前置條件已滿足的未完成任務，直到清單完成。

## 怎麼選批次

每一批從 `tasks.md` 裡第一個前置條件已滿足的未完成任務開始。能證明與起點安全平行的未完成任務可以加入同一批；無法證明時，該批只含起點那一個任務。

Phase 順序：

- Phase 1 完成後才做 Phase 2。
- Phase 2 完成前只選 Phase 2 以內的任務。
- 到達 User Story 或 Phase checkpoint 時，要先有有效的 Checkpoint 通過紀錄，才選下一個 Phase 的任務。
- Polish Phase 在欲交付的使用者故事任務完成後才選。

可以放進同一批的任務，要有 `[P]`、出現在 `Parallel Opportunities`，或能從檔案與依賴證明可平行，並且：

- 位於同一個 Phase gate 與同一個 Checkpoint 邊界內
- 寫入不同檔案
- 測試任務與其對應實作任務分成不同批次
- 服務層實作，與依賴它的路由、WebSocket 分派或前端串接分成不同批次
- Schema、型別或 migration，與依賴該結構的實作分成不同批次
- 依任務描述、Dependencies 或 Within Each User Story 給出的順序排批次

平行只涵蓋互不覆蓋的讀取、獨立驗證，以及不同檔案的修改。每個任務保留自己的 References、變更摘要、驗證證據與 checkbox。

## 上下文與變更範圍

只載入該任務正下方每一行 References 指向的契約部位。OpenAPI、DBML、interface、techstack 只讀被點名的片段。位址無法解析時，停止該任務並回報缺少或無效的位址。

後端任務讀該任務列出的後端部位，資料庫任務讀 DBML table，前端任務讀前端部位。任務描述與 References 衝突時回報衝突。

原始碼讀取目標任務描述中的目標檔，以及同目錄相鄰檔、既有測試或呼叫端，用來對齊既有實作模式。

變更只服務該任務的描述與 References。可以建立該任務需要的最小輔助型別、函式或檔案。

測試任務先寫入要求的斷言，並在對應實作完成前執行。失敗原因要對應尚未實作的目標行為。無法執行到這種失敗時，修正測試任務本身，並保持該任務未打勾。

實作任務先對上對應測試與該任務列出的契約部位，包含錯誤路徑。測試與契約矛盾時回報矛盾；此時停止，或只修正明確錯誤的測試。

## 驗證與打勾

每個任務用最接近的單元測試、整合測試、lint 或 typecheck，驗證它直接修改或新增的行為。無法自動驗證時，記錄原因與手動檢查證據。

驗證通過，或已有明確手動完成證據後，只把該任務的 checkbox 從 `[ ]` 改成 `[X]`，然後重讀 `tasks.md`，確認該任務狀態與下一個未完成任務。

驗證失敗時：

- 失敗屬於目標任務，而且失敗原因與紀錄中的不同：先更新 `失敗原因`，再修正並重新驗證。
- 重新驗證的失敗原因與紀錄相同：寫入 `阻塞` 與 `恢復條件`，不再修正。
- 失敗不屬於目標任務：寫入範圍外阻塞與要先修好的項目。同批已經通過的其他任務仍依各自證據打勾。

驗證仍失敗的任務保持 `[ ]`。

## Checkpoint

選擇某個 Checkpoint 之後的任務前，該 Checkpoint 要已有有效通過紀錄。通過紀錄無效或缺少時，本次只驗證該 Checkpoint。

本批做完 Checkpoint 之前的最後一個未完成任務後，打勾並驗證該 Checkpoint。相關任務都已打勾，仍要跑 Checkpoint 原文的驗證命令或手動檢查。

驗證通過時，在該 Checkpoint 下一行寫入：

```markdown
**Checkpoint status**: PASS
```

同一 Checkpoint 只保留一行狀態。通過紀錄只代表該 Checkpoint 原文描述的結果通過。

Checkpoint 之前仍有未完成任務時，既有 PASS 視為失效並移除。移除後重新驗證通過，才再寫入 PASS。

Checkpoint 失敗，且 `阻塞` 為空白時：

- 本次失敗原因與紀錄中的 `失敗原因` 不同，而且該 Checkpoint 之前的任務描述或 References 已指出涵蓋此次失敗行為的檔案：把本次失敗原因寫入 `失敗原因`，修正該檔案，再驗證同一個 Checkpoint。
- 本次失敗原因與紀錄相同，或沒有可寫入的修正：寫入 `阻塞` 與 `恢復條件`。

修正寫進所屬任務指向的目標檔案。已打勾任務保持完成狀態。重新驗證通過前，不寫入 PASS，也不選擇該 Checkpoint 之後的任務。`阻塞` 已有內容時，不再驗證或修正 Checkpoint。

## 何時結束

以下任一情況結束本次執行：

- `tasks.md` 沒有未完成任務，且每個已到達的 Checkpoint 都有有效通過紀錄。
- `implement-run.md` 的 `阻塞` 已有內容。
- checklist 未完成，且使用者未允許略過。

## 回報

結束時回報完成的任務 ID、修改摘要、驗證結果、是否已打勾、Checkpoint 結果、未完成任務、阻塞事項與恢復執行條件。
