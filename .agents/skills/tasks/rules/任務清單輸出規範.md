# Rule 1 - 任務清單的輸出位置

- 任務清單必須寫入該功能 `plan.md` 所在目錄的 `tasks.md`。
- 目標功能沒有 `testplan.md` 時，必須把缺少測試計劃寫入回覆並停止寫入 `tasks.md`。
- 不得把任務清單寫進 Skill 的 `templates/`。
- 不得另建與 `tasks.md` 並列的第二份任務清單。

## Good Example

- 任務清單與該功能的 testplan.md、plan.md 放在同一目錄。

```text
specs/001-online-pvp-1a2b/testplan.md
specs/001-online-pvp-1a2b/tasks.md
```

## Bad Example

- 功能目錄還沒有測試計劃，任務清單仍被寫進 Skill 樣板目錄。

```text
.agents/skills/tasks/templates/tasks.md
```

# Rule 2 - 階段來自測試計劃

- 任務清單必須依序包含 Phase 1 Setup、Phase 2 Foundational、testplan.md 的每個使用者故事章一個 Phase，以及 testplan.md 跨故事章一個 Phase。
- 使用者故事 Phase 的數量必須等於 testplan.md 的使用者故事章數量。
- 使用者故事 Phase 的標題、優先級與案例順序必須來自該章，不得另從 spec.md 重切故事。
- testplan.md 沒有跨故事案例時，不得建立空的跨故事 Phase。
- 骨架與範例中的故事、任務編號與端點名稱是已確認範例的填法。產出時必須改成這次 testplan.md 的故事與案例，不得照抄範例任務。

## Good Example

- 測試計劃有兩則使用者故事與一個跨故事章，任務清單就有對應的 Phase 3、Phase 4 與 Phase 5。

```markdown
## Phase 3: User Story 1 - 以暱稱與房號進入房間（Priority: P1）

## Phase 5: 跨故事 - 房間資料可再讀
```

## Bad Example

- 測試計劃只有兩則故事，任務清單仍照範例多寫一則沒有案例的故事。

```markdown
## Phase 5: User Story 3 - 猜中對方答案（Priority: P3）
```

# Rule 3 - 端點小節

- 使用者故事 Phase 與跨故事 Phase 必須用 `###` 為該章實際有案例的介面切開端點。
- 端點小節必須包含 **Codebase**。端點小節不得列出契約檔或 **References**。
- 某個介面在該章沒有案例時，不得為它開空的端點小節。
- 端點小節的順序必須沿該章 TDD 順序；同一介面的案例被另一個介面打斷時，必須分段開小節，不得把同一介面的任務集中到順序之外。

## Good Example

- 進房章先是後端案例，接著才是前端案例，所以前端小節排在後端小節之後。

```markdown
### 後端端點：後端房間 API

**Codebase**: `backend/src/rooms/`、`backend/tests/`

### 前端端點：前端對局畫面

**Codebase**: `frontend/src/`、`frontend/tests/`
```

## Bad Example

- 該章沒有資料庫案例，仍開一個空的資料庫端點。

```markdown
### 資料庫端點：PostgreSQL 持久化介面

**Codebase**: `backend/src/db/`
```

# Rule 4 - 每個案例三個 TDD 任務

- testplan.md 的每個原子案例必須依序產生紅燈、綠燈、重構三個任務。
- 三個任務的 **TDD 步驟** 必須分別是 `紅燈`、`綠燈`、`重構`。
- 任務在所屬 Phase 的順序必須等於該章 TDD 順序；同一案例內必須是紅燈、綠燈、再重構。
- 綠燈任務必須只做該案例通過所需的最小實作。
- 重構任務必須只整理該案例綠燈觸及的實作；沒有可做的結構調整時，完成條件是保持行為不變並確認該案例測試仍通過。
- 不列為案例不得產生任務。
- Setup 與 Foundational 沒有對應案例時，不得標 **TDD 步驟**。
- 同一章的紅燈、綠燈、重構不得標 [P]。
- 跨故事任務不得標 [Story]。

## Good Example

- BE-1.1 依序是紅燈、綠燈、重構，而且都指向同一個案例。

```markdown
- [ ] T006 [US1] 紅燈：在 `backend/tests/integration/enter-room.test.ts` 寫入 BE-1.1，並執行到預期失敗
  - **TDD 步驟**: 紅燈
- [ ] T007 [US1] 綠燈：在 `backend/src/rooms/enter.ts` 做 BE-1.1 通過所需的最小實作
  - **TDD 步驟**: 綠燈
- [ ] T008 [US1] 重構：只整理 BE-1.1 綠燈觸及的實作；沒有可做的結構調整時保持行為不變，並確認測試仍通過
  - **TDD 步驟**: 重構
```

## Bad Example

- 同一個案例把紅燈和綠燈合成一個任務，並把重構留到全部故事結束之後。

```markdown
- [ ] T006 [US1] 撰寫 BE-1.1 測試並實作進入房間
- [ ] T099 重構全部使用者故事
```

# Rule 5 - 每個任務只綁該案例的位址

- 每個任務正下方必須有 **References**。
- 一行 **References** 只能有一個位址。
- TDD 任務必須正好兩行 **References**：`testplan.md#{案例 ID}`，以及該案例契約位址的同一條位址。
- 後端任務不得引用 DBML 或畫面。資料庫任務不得引用 OpenAPI 或畫面。前端畫面任務不得引用 OpenAPI 或 DBML。
- Setup 與 Foundational 的每一行 **References** 必須是 `plan.md` 的一個標題，或 `techstack.md` 採用技術表的一個 Area。
- 端點小節與任務清單開頭不得要求先讀完整份 research.md、techstack.md、contracts/ 或 testplan.md。

## Good Example

- 進房紅燈同時指向測試計劃案例與該案例的進入操作。

```markdown
- [ ] T006 [US1] 紅燈：在 `backend/tests/integration/enter-room.test.ts` 寫入 BE-1.1，並執行到預期失敗
  - **TDD 步驟**: 紅燈
  - **References**: `testplan.md#BE-1.1`
  - **References**: `contracts/openapi.yaml#/paths/~1api~1rooms~1enter/post`
```

## Bad Example

- 前端任務改指 OpenAPI，而且沒有測試計劃案例位址。

```markdown
- [ ] T012 [US1] 紅燈：寫入 FE-1.1
  - **References**: `contracts/openapi.yaml`
```
